# План миграции данных GoFuture

План применяется в соответствии с [Очерёдностью выделения сервисов](./03-service-extraction-order.ru.md).

## Canary Releases

**Контекст.** Пока GoFuture выделяет сервисы, монолит продолжает обслуживать пользователей. Его обновления могут затронуть контракты и бизнес-правила, общие для монолита и нового сервиса. При единовременном переключении сервис сразу принимает все запросы по операции и начинает записывать данные. Ошибка, которая проявится на реальном трафике, может затронуть всех пользователей операции. Если сервис уже записал изменения, для возврата к монолиту их придётся сверить и перенести.

**Решение.** Использовать канареечное переключение до передачи записи сервису, если монолит может записывать изменения по запросам с обоих маршрутов. Команда QA проверяет оба маршрута. Нагрузочные тесты подтверждают готовность сервиса к ожидаемой нагрузке. После успешных проверок направить в сервис небольшую долю реальных запросов.

**Преимущества.** Ошибки сервиса, несовместимость контрактов и проблемы со временем отклика затрагивают меньшую долю запросов. До передачи записи команда может возвращать трафик в монолит изменением маршрута и повторять проверку после исправлений. Так выделение сервиса можно продолжать, даже если очередное обновление монолита меняет общий контракт или бизнес-правило.

## Общие правила миграции

Эти правила применяются к каждому сервису с учётом его этапов миграции.

1. Если сервису или его потребителям нужны записи из исходной БД, копировать их пакетами без остановки монолита. Отслеживать изменения с начала копирования. Применять эти изменения в целевой БД.
2. Во время канареечного переключения постепенно увеличивать долю запросов к новому сервису, пока он работает стабильно. Монолит записывает изменения по запросам с обоих маршрутов. При сбое вернуть запросы в монолит изменением маршрута.
3. Перед передачей записи сервису остановить запись переносимых данных в исходную БД. Применить оставшиеся изменения в целевой БД. Сверить записи в обеих БД на одной транзакционной позиции. После устранения блокирующих расхождений передать запись сервису. Направить оставшиеся запросы в сервис.
4. После передачи записи проверять согласованность данных автоматически. При сбое восстановить работу сервиса с сохранением изменений, которые он записал в свою БД.
5. Хранить исходные данные для восстановления не менее года после успешного завершения всех миграций (NFR-14).

## 1. Notification

**Граница данных.** Перенести данные о состоянии доставки уведомлений из общей БД монолита в БД сервиса Notification. Обе БД используют PostgreSQL. Монолит продолжает передавать данные о поездках для отправки уведомлений. AS-IS C3 показывает кеш данных об устройствах в Redis. До копирования уточнить источник данных об устройствах. Определить, какие записи истории доставки переносить.

Затем они прекращают запись данных о состоянии доставки. Новые задачи остаются в очереди RabbitMQ. Проверить чтение и запись в БД сервиса Notification. |

**Целевое состояние.** Сервис Notification обрабатывает уведомления после передачи сценариев из монолита. Сервис хранит и изменяет данные о состоянии доставки в своей БД.

## 4. Driver и Fraud

### Driver

**Граница данных.** Перенести данные водителей из таблицы `drivers` общей БД монолита в PostgreSQL сервиса Driver. Уточнить, где монолит хранит действующие назначения водителей. Перенести эти назначения в БД сервиса Driver. Booking продолжает хранить подтверждённое назначение водителя в данных поездки. Сведения о выплатах Driver получает из монолита до выделения Payouts.

### Fraud

**Граница данных.** Fraud хранит результаты оценок риска в своей PostgreSQL. Данные о поездках и платежах остаются у Booking и Payments. Сейчас компонент Fraud читает таблицы `bookings` и `payments` напрямую. При выделении сервиса Booking и Payments передают данные для оценки риска через контракты. До переключения определить, нужны ли Fraud или его потребителям результаты прошлых оценок риска. Если нужны, определить их источник.

Booking и Payments используют его результаты.                            | Если нужны прошлые результаты, перенести их по общим правилам. Сравнить оценки монолита и сервиса на одинаковых входных данных.     |
| Передать оценку риска сервису Fraud | Booking и Payments в монолите обращаются к сервису Fraud. Сервис возвращает результаты оценки риска и записывает их в свою БД. | Завершить начатые оценки в монолите. **Целевое состояние.** Fraud оценивает риск по данным от Booking и Payments и самостоятельно хранит результаты. Компонент Fraud в монолите прекращает оценку риска и прямое чтение `bookings` и `payments`.

## 7. Booking
